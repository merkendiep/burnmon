# Capture cloud Cowork tokens inside the container

> Update 2026-10-12 16:50 (measured): rank 2 does not work on this build. Settings has no Cowork page; the toggle is General > Tasks > "Only on this computer", it was ON, and a new session still ran in the cloud. See the update in `2026-10-12_cloud_cowork_sessions_proof.md`. The companion plugin (rank 1) is the only route left.

BurnMon cannot count cloud-run Cowork sessions from the laptop, and no documented per-user channel hands those token counts to a local tool. Usage still exists, though. It sits inside the cloud session's own Linux container, which keeps an ordinary Claude Code JSONL transcript with full `message.usage` on every assistant row (measured). BurnMon should ship a small **companion plugin**. Its Stop hook writes a whitelisted, deduplicated, usage-only JSONL after each turn, and the Desktop app's documented connected-folder bridge carries that file to a laptop drop folder. BurnMon reads the folder like any other source, so it still makes no network calls and opens no ports. One hop is unproven. Nobody has yet tested whether a hook can trigger the file delivery without the model. The fallback costs one small tool call per turn. Treat the result as a lower bound: in one measured session the transcript missed **about 6 percent of Opus cache reads and all Haiku side calls**. Two steps cost nothing and can happen today. Each user can turn off "Run new tasks in the cloud", and the Owner can turn off the org's cloud toggle if losing web and mobile Cowork is acceptable. OpenTelemetry carries exactly the right fields. But for cloud sessions it needs an internet-reachable collector and it captures every org member, so it is parked. Teleport, the Compliance API and every undocumented runner channel are out.

Evidence tags used below. **Measured** means observed on 2026-10-12, either on the user's Windows laptop or inside a cloud Cowork container on the same Team-plan account. **Documented** means an Anthropic page says it, with a link. **Inferred** means a conclusion drawn from combining the two that no source states.

## The laptop sees a 3 KB stub, the container keeps everything

On the laptop the gap is concrete (measured, laptop). Local Cowork transcripts are still written daily in the Microsoft Store install's `local-agent-mode-sessions` folder: **8 on 2026-10-12**. The one cloud session that day wrote no transcript. Its only local trace was `remote-session-spaces.json`, **3,174 bytes**, with a single key `entries` and no token fields. This matches the documentation. Cloud "sessions and files are saved to the member's Claude account" ([Team and Enterprise](https://support.claude.com/en/articles/13455879-use-claude-cowork-on-team-and-enterprise-plans)), and the agent loop runs "in an isolated, temporary sandbox on Anthropic-managed infrastructure" ([Architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)). Other open-source trackers have not reached this point yet. The three relevant issues are all about reading local `local-agent-mode-sessions` files, and they call cloud data "not on disk" ([Pacer #250](https://github.com/EricAndrechek/Pacer/issues/250), [llm-wiki #31](https://github.com/AlexanderMakarov/llm-wiki/issues/31), [AIChat #91](https://github.com/kellylford/AIChat/issues/91)).

The container tells a different story (measured, cloud container). The cloud runner is Claude Code with `CLAUDE_CODE_ENTRYPOINT=remote_cowork`. It writes a standard transcript at `/root/.claude/projects/-home-claude/<session-uuid>.jsonl`. The inspected file was 1,790,590 bytes with 209 rows. All **57 assistant rows** carried `message.usage`, spread over **22 distinct requestIds**. The usage block is a superset of what BurnMon already parses: `input_tokens`, `output_tokens`, `cache_creation_input_tokens` with the 5-minute and 1-hour split, `cache_read_input_tokens`, `output_tokens_details.thinking_tokens`, `service_tier`, `speed`, plus `iterations` and `fallback_credit`, whose meaning nobody documents. No row carries a cost field. Subagents write separate files under `<session-uuid>/subagents/agent-<id>.jsonl`, four files of 426 to 494 KB in this session. All their rows are `isSidechain=true`, and each has its own usage. The container holds only the current session, with no history of earlier ones.

Two caveats attach to this format. Anthropic says the transcript entry format "is internal to Claude Code and changes between versions" ([Manage sessions](https://code.claude.com/docs/en/sessions)). BurnMon already lives with that risk for local sessions. The second caveat is a measured inconsistency. Rows report version 2.1.296, while the container's `CLAUDE_CODE_VERSION` says 2.1.42. A parser should key on fields, not on version strings.

## Seven routes ranked: one to build, one to do today

| Rank | Route | Cloud tokens per session? | Fits no-network, no-ports, documented-only? | Verdict |
|---|---|---|---|---|
| 1 | Companion plugin: Stop hook writes usage JSONL, delivered to a connected laptop folder | Yes, lower bound | Yes. BurnMon reads a folder; the Desktop app does the transfer | **Build**, gated on tests 3 to 7 |
| 2 | Keep sessions local with the per-user and Owner toggles | Not needed: local transcripts return | Yes | **Do now**, stopgap only |
| 3 | Manual import of the Owner's Analytics spend CSV | No. Daily, per user per model | Yes, if a human downloads the file | Optional reconciliation, later |
| 4 | Cowork OpenTelemetry to a user-run collector that writes JSONL | Yes, per request with cost | Conflicts with no-ports and with org-wide scope | **Park** |
| 5 | Optional add-on to rank 1: read SDK `result` lines in `/tmp` | Session totals incl. side calls | Undocumented runner file | Not in v1 |
| 6 | Teleport a cloud session to a local transcript | Unknown | Undocumented for Cowork | Test once, expect to kill |
| 7 | Claude Desktop on 3P providers | Yes, all sessions stay local | Yes, but metered billing and a separate deployment | Not a BurnMon solution |

Rank 1 wins because it is the only route that meets all of BurnMon's rules and still gives per-session, per-request numbers. Hooks and plugins are user configuration, not vendor endpoints. The delivery uses a documented feature: "A cloud session can read and write files in folders you've connected on your computer" through the Desktop app ([Web, desktop and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)). Rank 2 is cheaper but not durable, because local mode is shrinking (see the next section). Rank 3 is the only documented source that would cover web and mobile sessions, which rank 1 cannot reach. Even so, it gives no session detail.

Three tests gate the build. First, does a user-installed plugin's Stop hook fire in a cloud Cowork session (test 3)? Second, does the hook see the final assistant row of the turn (test 4)? Third, can a hook of type `mcp_tool` call `device_commit_files`, so delivery needs no model (test 5)? If the third fails, the model-prompted fallback must stay under a per-turn token budget (test 6) before the build goes ahead.

## The cheapest step: keep new sessions local while that still works

For a Team-plan account, local Cowork has not been removed, and no removal date has been announced (documented). Two switches decide where a session runs. Per user, "You can switch modes when starting a new session by clicking the "Beta" button in the upper right corner, or by navigating to Settings > Cowork and toggling Run new tasks in the cloud on or off". A session "stays in the cloud or local" once started ([Cowork in the cloud](https://support.claude.com/en/articles/15811196-what-to-expect-with-claude-cowork-in-the-cloud)). Org-wide, Team has "Run Cowork in the cloud" in Organization settings > Cowork, **on by default for Team** and off by default for Enterprise. An Owner can turn it off at any time ([Team and Enterprise](https://support.claude.com/en/articles/13455879-use-claude-cowork-on-team-and-enterprise-plans)). The architecture page confirms that an org can turn cloud sessions off "while leaving local desktop Cowork available" ([Architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)).

The immediate step, then, has two parts. The user switches off "Run new tasks in the cloud" on the laptop and checks the Beta button whenever starting a session. If the user is an Owner, they decide whether the org toggle goes off too. That decision affects every member, and web and mobile Cowork stop working, because those surfaces "run in Anthropic's cloud" only ([Team and Enterprise](https://support.claude.com/en/articles/13455879-use-claude-cowork-on-team-and-enterprise-plans)) (inferred consequence). The default value of the per-user toggle on Team is not documented. The measured mix of 8 local sessions and 1 cloud session in one day fits either a local default or a per-session choice.

This is a stopgap for three documented reasons. On Pro and Max, new Cowork tasks have run in the cloud since 2026-10-06, and "you can't switch back" ([Web, desktop and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)). Under the new unified experience, "tasks run in the cloud, and there's no option to run them locally" ([Cowork in the cloud](https://support.claude.com/en/articles/15811196-what-to-expect-with-claude-cowork-in-the-cloud)), and unified "is meant to replace both over time" ([Enterprise unified setup](https://support.claude.com/en/articles/17444462-set-up-and-manage-the-new-unified-claude-experience-for-your-enterprise-organization)). Finally, the 30-day notice promise names Enterprise admins only ([Cowork and chat are one Claude](https://support.claude.com/en/articles/16761823)), so a Team account could lose local mode without notice (inferred). Two escape routes remain but do not help BurnMon directly. Claude Code in the desktop app stays local ([Web, desktop and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)). Claude Desktop on 3P keeps every Cowork session in a local VM, but billing becomes token-metered by the cloud provider ([3P feature matrix](https://claude.com/docs/third-party/claude-desktop/feature-matrix)).

## The companion plugin: Stop hook, field whitelist, last-row dedup

### Hooks already run in cloud containers

Measured, cloud container: Claude starts with `--settings /root/.claude/launcher-settings.json`. The platform's own Stop hook ran 5 times in the inspected session, at 26 to 31 ms each. The account's synced plugins land under `/root/.claude/plugins/synced/`, and their `hooks/hooks.json` is live. One of the account's own plugins has a PreToolUse hook, and it fired 4 times. It failed with exit code 127 only because PowerShell is not installed in the container. `python3` is present. Documented: cloud sessions "don't read your local ~/.claude/settings.json", and plugin hooks "merge with your user and project hooks" ([Hooks](https://code.claude.com/docs/en/hooks)). Inferred: a BurnMon plugin with a Python or bash Stop hook will sync into every cloud container of the account and run at zero token cost. Measured: plugin MCP servers are skipped (`CLAUDE_CODE_SKIP_PLUGIN_MCP_SERVERS=1`), so the plugin cannot bring its own MCP server.

Stop is the right trigger. It fires after every turn. SessionEnd is meant for "side effects like logging or cleanup", but it has a 1.5 second default budget ([Hooks](https://code.claude.com/docs/en/hooks)), and cloud VMs are stopped after idle time rather than ended cleanly ([Enterprise unified setup](https://support.claude.com/en/articles/17444462-set-up-and-manage-the-new-unified-claude-experience-for-your-enterprise-organization)). So SessionEnd is unlikely to fire (inferred, untested).

### Whitelist, never blacklist

The hook copies named fields into a new object and drops everything else. Keep: row `timestamp`, `sessionId`, the remote session id from `CLAUDE_CODE_REMOTE_SESSION_ID`, `requestId`, `message.id`, `message.model`, `isSidechain`, `agentId`, the four token counts, the 5m and 1h cache-write split, `thinking_tokens`, `service_tier` and `speed`. Measured, cloud container: fields that would leak content include `message.content`, `wireToolInputs` (commands, prompts, URLs, queries, paths), every `attachment` row (system prompt, prompt, stdout, stderr), `last-prompt.lastPrompt`, `ai-title.aiTitle`, `cwd` and `gitBranch`. A blacklist would miss the next field Anthropic adds, which is why the plugin must whitelist. Measured size: a 22-request extract came to **6,350 bytes, about 288 bytes per request**. BurnMon's export rule is satisfied as long as nothing outside the whitelist ever reaches the drop folder.

### Dedup: keep the last row per requestId plus message.id

One API request can be written as several rows. Measured, cloud container: the main file had 57 rows for 22 requests. In the subagent files, **8 of 26 multi-row requests had different usage on different rows**. One example showed `output_tokens` 8 on the first row (stop_reason null) and 148 on the last (stop_reason tool_use). Summing every row overcounts. Taking the first row undercounts output. The rule is to group by (`requestId`, `message.id`) and keep the last row. BurnMon should apply the same rule on ingest, because the hook rewrites the whole session file each turn. Upserting on that key makes repeated deliveries idempotent and also covers any future teleported copy.

### Subagent files are not optional

Each subagent writes its own JSONL with its own usage (measured, 4 files in one session). The hook must glob `<session-uuid>/subagents/agent-*.jsonl` alongside the main file. It should tag those rows with `isSidechain` and `agentId`, so BurnMon can show subagent spend separately.

### Delivery is the weak link

Writing the file is the easy half. Getting it to the laptop is the hard half. Measured, cloud container: `/mnt/user-data/outputs` is an rclone FUSE mount of an Anthropic-hosted filestore keyed to the session, not a folder on the laptop. Bytes reach the laptop only through the Desktop app's connected-folder bridge. In the session's tools that bridge is `device_commit_files`, which copies a file from outputs to a connected folder server-side, up to 50 files and 30 MB per file. Two ways to call it exist. An `mcp_tool` hook is a documented hook type ([Hooks](https://code.claude.com/docs/en/hooks)), and the installed binary contains it (measured, 10 string matches). It would cost zero tokens and need no model cooperation. But the `remote-devices` server is not in `--mcp-config`. It appears to arrive over the SDK channel instead (measured), so nobody knows whether a hook can address it. Hooks that match the same event run in parallel, so the commit should run one event after the write, for example on the next UserPromptSubmit. The fallback is a UserPromptSubmit hook that injects `additionalContext` asking the model to commit the file. That costs roughly **100 to 300 tokens per turn** (inferred from tool-call size, not measured) and depends on the model complying. A Stop hook that blocks to force the commit is worse: it forces an extra model turn every time, and the forced turn's own usage never gets exported.

### Known gaps, stated up front

A plugin built this way will undercount in five places. **Side calls never reach the transcript.** Measured, cloud container: at the same turn boundary, the deduplicated transcript showed 18 Opus requests with 2,971,013 cache-read and 14,602 output tokens. The SDK `result` record showed 3,160,549 cache-read and 14,611 output tokens for Opus, at a list-price `costUSD` of 1.7874. That is a gap of **189,536 cache-read tokens, about 6 percent**. The same record also showed **39,411 input and 9,191 output Haiku tokens**, and no transcript row anywhere has a Haiku model. Nothing names these calls. A post-turn memory pass and title generation fit the pattern (inferred). **The final turn is late.** With a one-event lag, the last turn arrives only if the user prompts again, unless an `mcp_tool` commit on Stop can see the freshly written file. **Transcript lag.** `transcript_path` "may lag the in-memory conversation" ([Hooks](https://code.claude.com/docs/en/hooks)), so the Stop hook may miss the final row. **VM reclaim.** A reclaimed VM restores conversation history but not background work ([Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)). Whether restored rows keep `message.usage` is untested. **Web and mobile sessions are unreachable.** A cloud session reaches connected folders "only while the desktop app is open on that computer and the session was started on desktop or is a scheduled task" ([Web, desktop and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)). Sessions started on web or mobile cannot deliver at all. Neither can any session while the app is closed.

The SDK `result` lines in `/tmp/claude-preload.out` would close the side-call gap, because they carry cumulative per-model totals including Haiku (measured). But that file is an undocumented runner internal. It exists only because `CLAUDE_CODE_TEE_SDK_STDOUT` is set, and it is lost when the VM is reclaimed. Every other line in it carries full message content. At most it belongs behind an off-by-default flag that extracts numeric fields from `type == result` lines only. It is not part of v1.

## OpenTelemetry carries the right fields to the wrong place

Cowork OTel is the only documented channel with per-request `input_tokens`, `output_tokens`, `cache_read_tokens`, `cache_creation_tokens`, `model`, `cost_usd` and `session.id` on the `api_request` event ([Cowork monitoring](https://claude.com/docs/cowork/monitoring)). The Help Center says it "covers Cowork sessions that run in the cloud (on desktop, web, and mobile)", on Team and Enterprise, from Desktop 1.22209.3 ([Monitor Cowork with OTel](https://support.claude.com/en/articles/14477985-monitor-cowork-activity-with-opentelemetry)). On paper it is the best data source. It fails BurnMon's design for three reasons.

First, ports. The exporter "runs inside the Cowork VM" ([Cowork monitoring](https://claude.com/docs/cowork/monitoring)). The cloud sandbox "can't reach private, internal, link-local, or cloud-metadata addresses", and all traffic passes "a mandatory proxy" ([Architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)). Inferred, not stated verbatim: for cloud sessions the collector must be a public HTTPS host, never localhost or a file on the laptop. Someone has to run a listening OTLP/HTTP receiver on the internet, or tunnel one to the laptop. BurnMon could stay clean by reading the JSONL that a separate collector writes through the OTel file exporter, which emits one JSON object per line ([fileexporter](https://github.com/open-telemetry/opentelemetry-collector-contrib/blob/main/exporter/fileexporter/README.md)). But the product would then depend on an open port, which is exactly what BurnMon exists to avoid. The device-level `otlpEndpoint` can point at localhost, but only for sessions running on the device ([3P telemetry](https://claude.com/docs/third-party/claude-desktop/telemetry.md)). Those sessions already have transcripts.

Second, scope. The endpoint is set once per organization by an admin in claude.ai, and "Events are only exported when an admin configures an OTLP endpoint" ([Monitor Cowork with OTel](https://support.claude.com/en/articles/14477985-monitor-cowork-activity-with-opentelemetry)). Every member's events flow to it. On a Team-plan account shared with others, a personal BurnMon would collect colleagues' data. That is acceptable only on an org the user alone controls (inferred).

Third, content. The `user.email` and `workspace.host_paths` attributes are always present. Prompt and response text depend on the device key `otlpContentCapture`, which defaults to full content on first-party when unset ([Cowork monitoring](https://claude.com/docs/cowork/monitoring)). The collector would have to strip them before anything reached BurnMon. The `api_request` token fields survive a metadata-only setting, so the data BurnMon needs is not at risk from that setting. OTel stays parked. It becomes the right answer only if Anthropic documents a per-user, opt-in export to a file or a local process.

## Teleport and the excluded routes

Teleport is the only documented feature that pulls cloud conversation history onto local disk. It "loads the full conversation history into your terminal" ([Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)). A community report shows the result as an ordinary project `.jsonl` ([#28039 mirror](https://claudeissues.com/issue/28039-web-cli-teleported-sessions-not-appearing-in-resume-session-list)). Four facts make it a poor fit. It is documented for Claude Code cloud sessions and requires the same git repository, a pushed branch and a clean tree. Cowork sessions have no repository. Repo-less teleport has broken before ([#74277 mirror](https://claudeissues.com/issue/74277-bug-teleport-stops-working-for-sessions-with-no-repo)). The Compliance API treats `cowork_remote` sessions as a separate class from Claude Code cloud sessions ([Compliance sessions](https://platform.claude.com/docs/en/manage-claude/compliance-sessions)). And teleport is interactive, gives a one-time snapshot, and has no headless form. Nobody knows whether `message.usage` survives the copy. One manual test settles it.

These routes are excluded outright:

| Route | Why excluded |
|---|---|
| Compliance API session transcripts | Enterprise only. BurnMon would call the network. "Token usage and cost: No" ([Compliance sessions](https://platform.claude.com/docs/en/manage-claude/compliance-sessions)) |
| Enterprise Analytics API `cost_report` | Enterprise only. Primary Owner key. Network calls. No session dimension ([Analytics APIs](https://platform.claude.com/docs/en/manage-claude/analytics-api.md)) |
| Admin Usage and Cost API, Claude Code Analytics API | Cover Console API usage, not claude.ai Cowork ([Usage and Cost API](https://platform.claude.com/docs/en/manage-claude/usage-cost-api)) |
| Scraping Settings > Usage | Undocumented endpoint. Shows plan limits, not tokens ([Cowork and chat are one Claude](https://support.claude.com/en/articles/16761823)) |
| Container messaging socket, session ingress URL, `sbx-telemetry-collector`, the filestore's API URL | Undocumented vendor endpoints (measured to exist, never to be used) |
| `claude -p --cloud <id>` asking the session for its usage | Spends tokens and changes the session ([Claude Code in the cloud](https://code.claude.com/docs/en/claude-code-on-the-web)) |
| claude.ai data export | Manual. Primary Owner only on Team. No documented token data ([Org export](https://support.claude.com/en/articles/13346720-export-your-organization-s-data)) |
| "Import Cowork transcripts into Claude Code" | Claimed by a blog ([SmartScope](https://smartscope.blog/en/blog/claude-cowork-local-option-cloud-october-6-2026/)). The support article it cites says nothing of the kind. `claude import` imports configuration, not transcripts ([CLI reference](https://code.claude.com/docs/en/cli-reference)) |

The Analytics spend CSV is not excluded. It is documented and Owner-only on Team, with one row per person per model, `total_prompt_tokens` and `total_completion_tokens`, refreshed daily, with no cache split and no sessions ([Usage analytics](https://support.claude.com/en/articles/12883420-view-usage-analytics-for-team-and-enterprise-plans)). A human can download it and drop it in a folder, and a BurnMon importer could then keep only the user's own row and discard the email column. It is a reconciliation check and the only cover for web and mobile sessions. It is not a session source.

## Kill criteria

These thresholds are proposals for the owner to confirm, not findings. **Kill the plugin route** if a user-installed plugin's Stop hook does not run in cloud Cowork sessions started on desktop (test 3). Kill it as well if the Stop hook consistently misses the turn's final assistant row and no event-shift workaround recovers it (test 4). **Demote delivery to manual** if the `mcp_tool` hook cannot reach `device_commit_files` and the model-prompted fallback either fails on more than 1 turn in 10 or costs more than 500 tokens per turn (tests 5 and 6). **Stop the build immediately** if any field outside the whitelist appears in a delivered file. **Downgrade to "estimate, labelled as such"** if, over three sessions, plugin totals fall more than 10 percent below the SDK `result` totals. Abandon the route if the gap exceeds 25 percent. **Add the CSV importer, or accept a visible blind spot,** if more than a third of the user's cloud sessions start on web or mobile (test 9). **Switch to OTel** only if Anthropic documents a per-user export that needs no public listener. **Kill teleport** if `claude --teleport` refuses a `cse_` session id or the local copy lacks `message.usage` (test 13).

## Conclusion

The question changed during research. It started as "how can a local tool reach the cloud". It became "how can the cloud session hand its own numbers to a local folder". Anthropic already gives the user both pieces: hooks that run inside the cloud container, and a connected-folder bridge back to the laptop. Neither needs BurnMon to touch the network. The real risk is not privacy or rule-breaking but completeness. Transcripts were never the full bill, even locally. Cloud runners add side calls that leave no row, and sessions started on web or mobile have no way home. BurnMon should present cloud Cowork as "measured from transcript, lower bound" and show a coverage indicator. One candidate signal for that indicator is the entry count in `remote-session-spaces.json`, if test 2 shows that entries map to cloud sessions. That keeps the product honest even when a number is incomplete.

Local Cowork on a Team-plan account is a dwindling window, not a strategy. The unified experience removes it, and Pro and Max have already lost it. Teams have no notice guarantee. Building the plugin now, while local transcripts still exist to compare against, gives BurnMon a calibration baseline it will not have later.

## Live tests, in order

1. Laptop: switch off Settings > Cowork > "Run new tasks in the cloud", start a desktop Cowork session, and confirm that a new transcript appears in `local-agent-mode-sessions` and that `remote-session-spaces.json` does not grow.
2. Laptop: start one cloud session and diff the field names and entry count of `remote-session-spaces.json` before and after. Read names only, no values. This decides whether it can drive a "cloud sessions not counted" indicator.
3. Cloud: install a minimal plugin on the user's own account (not org-wide) with a Python Stop hook that writes only row counts to `/mnt/user-data/outputs/burnmon/`. Confirm that it fires, and check whether the file shows up as a deliverable in the UI.
4. Cloud: in that hook, record the assistant-row count at Stop and compare it with the count at the next turn, to measure transcript lag.
5. Cloud: add an `mcp_tool` hook on UserPromptSubmit that calls `remote-devices` `device_commit_files` into a throwaway connected folder. Record success, approval prompts and errors.
6. Cloud, only if test 5 fails: use `additionalContext` to ask the model to commit, and measure the added tokens per turn from the transcript over 10 turns.
7. Cloud: commit to a path that already exists, to learn the overwrite and mtime-guard behaviour. Fall back to per-turn file names if it refuses.
8. Laptop and cloud: close the Desktop app during a turn, reopen it, and check whether the backlog file arrives on the next commit.
9. Web and mobile: start one cloud session on each and confirm that delivery fails, as documented. Then count over two weeks what share of cloud sessions started off desktop.
10. Cloud: let a session idle until the VM is reclaimed, resume it, and check that restored rows keep `message.usage` and that the rewrite does not double-count after BurnMon's upsert.
11. Cloud, read-only: over three sessions, compare plugin totals with the numeric fields of the SDK `result` lines to set the lower-bound gap against the kill thresholds.
12. Owner console: check whether the Team admin console offers "Chat and Cowork unified", and whether plugins and hooks still sync into unified sessions.
13. Laptop: run `claude --teleport` with one Cowork `cse_` session id. Kill the route if it refuses, or if the local JSONL lacks `message.usage`.
14. Owner, optional: download one Analytics spend CSV and compare the user's own Cowork row with BurnMon's daily total. Check whether the Product column separates Cowork from chat.
15. OTel, optional and only on an org the user alone controls: point the Cowork OTLP endpoint at a temporary public collector, run one cloud session, and confirm whether `api_request` events arrive. This settles contradiction 1.
