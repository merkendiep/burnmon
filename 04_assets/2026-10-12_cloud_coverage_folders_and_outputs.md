# Cowork cloud sessions: folders, outputs and reaching the user's computer (as of 2026-10-12)

Method note: support.claude.com articles were downloaded as raw HTML on 2026-10-12 and converted to text, so quotes below are verbatim from the live pages (with each page's "Updated" stamp where shown). claude.com/docs pages were fetched as .md. Community reports are marked [COMMUNITY]; everything else is official Anthropic documentation [DOC].

Plan context: Team plan has the Chat/Cowork selector; the "new Claude experience" (unified) is rolling out to Pro and Max first. "Team and Enterprise organizations keep chat and Claude Cowork as they are today" [DOC] [Architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview). For Team: "Team plans: on by default. An owner can turn it off any time from the 'Run Cowork in the cloud' toggle." [DOC] [Team and Enterprise](https://support.claude.com/en/articles/13455879-use-claude-cowork-on-team-and-enterprise-plans)

## Q1. Default folders for every new cloud session; what Projects do; org/admin policy

### Takeaway
No documented user or org setting connects a folder to every new cloud session on standard (first-party) Claude Desktop. The closest documented mechanism is the MDM key `allowedWorkspaceFolders` with `isDefaultSelected: true`, which pre-selects a folder chip on the new-task page, but that field is documented only in the third-party (3P) Desktop docs, and the standard Team/Enterprise policy article lists `allowedWorkspaceFolders` without it. Projects can hold local folders and the docs say a session started from a project gets them mounted, but the newer support pages say projects tied to a local folder work "on desktop only", and community bug reports show project folders often not mounting in new sessions.

### Cited Findings
Cloud sessions and folders (general)
- "Attach folders manually. Reaching files or tools on your computer requires the Claude Desktop app to be open and connected." (listed under "These differences apply to any cloud session, including on desktop") [DOC] [What to expect with Claude Cowork in the cloud, updated over 3 weeks ago](https://support.claude.com/en/articles/15811196-what-to-expect-with-claude-cowork-in-the-cloud)
- "Your folders stay on your computer. Claude reaches only the folders you've connected, through the desktop app, and only while it's open. When a task needs a file in the cloud, Claude fetches a copy of just that file." [DOC] [Use Claude Cowork on web, desktop, and mobile, updated this week](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)
- "Local file access is limited to folders the member has connected on the desktop, and each local tool call is checked against the member's permissions before it runs. If the desktop app is offline, a session in the cloud can't reach the device." [DOC] [Architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)

Trusted folders
- The unified-experience article: "Files: Files Claude creates appear alongside the conversation. In Claude Desktop, the folder Cowork saved its work to is still there. Look for Storage folder in Settings. Folders you gave Cowork access to are listed under Trusted folders." [DOC] [Claude Cowork and chat are one Claude](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude)
- The exact UI sentence "Trusting a folder doesn't add it to new sessions" (from the brief) was not found on any public page; a search for it returned only unrelated Claude Code trust-prompt issues. Not verifiable from public docs.
- Changelog v1.12603.1 (2026-06-11), Cowork: "Fixed remote sessions re-prompting for access to folders you had already trusted." This implies trust suppresses the access prompt; it does not say trust connects the folder. [DOC] [Claude Desktop changelog](https://claude.com/docs/cowork/changelog)

Projects
- Support article: "Projects in Claude Cowork let you group related tasks into dedicated workspaces with their own files, context, instructions, and memory. ... New projects you create in Cowork are saved to your Claude account, so you can pick them up from your other devices, and projects you create from a folder on your computer stay on that computer." Project contents include "Context: Add a local folder, link a chat project, or paste in a URL for Claude to reference." Limitation: "Projects you create from an existing folder on your computer stay on that computer and aren't saved to your Claude account." [DOC] [Organize your tasks with projects in Claude Cowork, updated over 3 weeks ago](https://support.claude.com/en/articles/14116274-organize-your-tasks-with-projects-in-cowork)
- The support article does not state that a project's folders are mounted automatically in each session.
- Docs guide (claude.com/docs) does state it: "Folders: One or more local folders Claude can read and write inside this project's sessions" and "Select a project in the sidebar to start a new Cowork session with that project's folders mounted and instructions applied. Files Claude creates land in the project's folders". It also says "Projects live on your computer. They aren't synced to the cloud or shared with other people." [DOC] [Organize work with projects (claude.com/docs)](https://claude.com/docs/cowork/guide/projects)
- Conflict: the docs guide says Cowork projects live on the computer only; the support article (and the Team article) say new Cowork projects are saved to the Claude account and only folder-based projects stay local: "For local sessions, project data is stored on the user's computer; for sessions in the cloud, projects are saved with the member's Claude account." [DOC] [Team and Enterprise](https://support.claude.com/en/articles/13455879-use-claude-cowork-on-team-and-enterprise-plans). The docs guide reads as the older local-mode description.
- "Projects tied to a local folder support Cowork sessions on desktop only, and Cowork won't change a project's contents, so add anything you want to keep to the project yourself." [DOC] [Web, desktop, and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)
- "There are no separate admin controls for projects, so owners cannot restrict project creation at the organization level at this time." [DOC] [Team and Enterprise](https://support.claude.com/en/articles/13455879-use-claude-cowork-on-team-and-enterprise-plans)
- One folder in several projects: not documented either way. The docs guide says "Use an existing folder to point at a folder you already work from" and "You can attach more folders ... at any time", with no stated exclusivity. [DOC] [Projects guide](https://claude.com/docs/cowork/guide/projects)
- [COMMUNITY] GitHub issue anthropics/claude-code #76187 (Windows): "Projects still show their context folders in the Context panel, but every new session starts with zero folders actually attached." Expected behavior per reporter: "New sessions should inherit and mount the project's context folders automatically ... Both worked exactly this way before the July 8 update." A 2026-09-09 comment (Desktop 1.49585.0) reports the project folder disappearing after reopening the project and `get_device_info` returning `"connectedFolders": []`; "Re-adding the folder mid-session works as a workaround." A 2026-08-27 comment (Desktop 1.37937.3) reports a project listing 10 local folders with "Zero of the ten folders" mounted. No Anthropic staff response on the page. [Issue #76187](https://github.com/anthropics/claude-code/issues/76187)

Admin / org policy
- Standard Desktop policy article: "Administrators on Team or Enterprise plans can control Claude Desktop through system policies." Windows uses Group Policy/Intune under `HKLM:\SOFTWARE\Policies\Claude`. Key `allowedWorkspaceFolders`, type "string[] (JSON)", default "Unrestricted", description "Filepath or filepaths the user can mount to Cowork". No pre-select field is listed. [DOC] [Enterprise configuration for Claude Desktop, dated September 2, 2026](https://support.claude.com/en/articles/12622667-enterprise-configuration-for-claude-desktop)
- 3P configuration reference: `allowedWorkspaceFolders` is `object[]`; field `isDefaultSelected` (boolean): "Shows as a folder chip on the new-task page and skips the trust prompt. Users can remove it." Also "Applies to Cowork and Code sessions and to the project folders a chat reads." [DOC] [Configuration reference (3P)](https://claude.com/docs/third-party/claude-desktop/configuration)
- 3P local-access page: "`isDefaultSelected`: When `true`, the folder appears already selected on the new-task page and skips the trust prompt. Users can remove it." [DOC] [Desktop and filesystem access (3P)](https://claude.com/docs/third-party/claude-desktop/local-access)
- Changelog v1.14271.0 (2026-06-18), under the **3P** heading: "Added a per-folder pre-select option to `allowedWorkspaceFolders` so an administrator-configured folder can appear as a ready chip when users start a new task, and removed the 'Create workspace folder?' prompt for administrator-configured folders." Same release: "Added `~` and environment variable expansion (such as `%APPDATA%` and `%OneDriveCommercial%`) to the `allowedWorkspaceFolders` setting". [DOC] [Changelog](https://claude.com/docs/cowork/changelog)
- Unified Enterprise article: device policy "On managed computers, limits which folders can be connected, disables user-added local MCP servers and extensions, and can require sign-in to your organization." No default-folder control is mentioned. [DOC] [Set up and manage the new unified Claude experience for your Enterprise organization](https://support.claude.com/en/articles/17444462-set-up-and-manage-the-new-unified-claude-experience-for-your-enterprise-organization)

### Inferences
- On standard Team-plan Desktop, the only documented default-folder lever is an admin policy that restricts folders; a documented "pre-select for every new task" exists only for 3P deployments. Whether the 1P app honors `isDefaultSelected` from the `HKLM\SOFTWARE\Policies\Claude` registry key is undocumented and would need a live test.
- Even where it applies, `isDefaultSelected` acts on "the new-task page" of Claude Desktop, so it would not cover sessions started on web or mobile, and "Users can remove it."
- A Project with the BurnMon folder is the closest per-user mechanism, but it covers only sessions started inside that project on desktop, and community reports show the mount is unreliable on Windows in July to September 2026 builds.

### Gaps
- No public doc text for the Settings > General > Tasks "Trusted folders" panel or its sentence "Trusting a folder doesn't add it to new sessions."
- Not documented whether one local folder can be attached to several projects.
- Not documented whether `isDefaultSelected` works on first-party Team installs, or whether it pre-selects for cloud (not only local) new tasks.

## Q2. Where /mnt/user-data/outputs files end up

### Takeaway
Documented: files Claude "delivers" are saved to the Claude account and can be previewed and downloaded from the session on any surface; working files not handed back are discarded when the cloud sandbox ends. There is no documented automatic sync or download of cloud-session outputs to a folder on the computer. The `~/Claude/` or `~/Documents/Claude/` statement is from the 3P data-storage page and describes local Desktop writing Artifacts and scheduled-task results; nothing documents it for cloud sessions on standard Desktop.

### Cited Findings
- "Save what you want to keep. Files Claude delivers are saved. Working files it doesn't hand back aren't kept or referenced after the session ends." and "Your connectors stay linked across sessions and devices, and files Claude delivers to you are saved." [DOC] [Cowork in the cloud](https://support.claude.com/en/articles/15811196-what-to-expect-with-claude-cowork-in-the-cloud)
- "In a session in the cloud, the agent loop and code execution run in an isolated, temporary sandbox on Anthropic-managed infrastructure. Each session gets its own sandbox, created when the session starts and destroyed when it ends" and "sessions and files are saved to the member's Claude account." [DOC] [Architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)
- Claude "Delivers finished outputs to your session, where you can preview and download them." [DOC] [Get started with Claude Cowork, updated this week](https://support.claude.com/en/articles/13345190-get-started-with-claude-cowork)
- "Pick up the finished output wherever you are. For example, start a task in the Chrome side panel while you're looking at a dashboard, then pick it up on desktop to work with the downloaded files." Feature table: "Preview files Claude creates" available on Desktop, Web and Mobile. [DOC] [Web, desktop, and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)
- Unified experience: "Files Claude creates appear alongside the conversation. In Claude Desktop, the folder Cowork saved its work to is still there. Look for Storage folder in Settings." and "Claude can create documents, spreadsheets with working formulas, and presentations you can open in PowerPoint. Download them and use them anywhere". [DOC] [Claude Cowork and chat are one Claude](https://support.claude.com/en/articles/16761823-claude-cowork-and-chat-are-one-claude). The "Storage folder" sentence refers to where (local) Cowork saved its work before the change; it does not say cloud outputs are written there.
- 3P data-storage page (scope: "How Claude Desktop on 3P identifies users and where it stores conversations, settings, and credentials on disk"; "Claude Desktop on 3P stores everything under a dedicated directory, separate from standard Claude Desktop"): "Separately from the application-data directory, Claude Desktop writes user-visible outputs (Artifacts and scheduled-task results) to ~/Claude/ in your home directory, or ~/Documents/Claude/ on legacy installs. This folder is intended for you to browse directly and is not removed when you delete the application-data directory." The same page describes each local session's working directory with "an outputs/ subdirectory for files Claude creates." [DOC] [User identity and local data (3P)](https://claude.com/docs/third-party/claude-desktop/data-storage)
- Changelog v1.11187.4 (2026-06-05): "Updated the New project folder picker to default to your Claude data folder (~/Claude/Projects) instead of ~/Documents." and v1.26832.0 (2026-08-06): read-only `allowedWorkspaceFolders` entries mean "Claude is directed to put modified copies in the session outputs folder." [DOC] [Changelog](https://claude.com/docs/cowork/changelog)
- Dispatch: "When Claude finishes a task that produces a file, you can access it directly from mobile or find it on your desktop at the location Claude specifies." (Dispatch runs on the desktop computer, not a cloud sandbox.) [DOC] [Assign tasks from anywhere in Claude Cowork](https://support.claude.com/en/articles/13947068-assign-tasks-from-anywhere-in-claude-cowork)
- Scheduled tasks "work with your connectors and the files saved to your Claude account." [DOC] [Schedule recurring tasks in Claude Cowork, updated this week](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork)

### Inferences
- A file written to /mnt/user-data/outputs in a cloud session lives in the account (if "delivered") and in the ephemeral sandbox; reaching the laptop requires either an explicit device write through a connected folder or a manual download by the user. No documented passive sync path exists.
- The ~/Claude/ statement is 3P-scoped and about local execution; applying it to standard Desktop cloud sessions would be an assumption.
- A dotfile path (.burnmon/cloud/latest.jsonl) written by a hook is a "working file" unless it is delivered to the user; the docs say undelivered working files "aren't kept".

### Gaps
- No doc defines what counts as "delivered" (e.g. whether every file under /mnt/user-data/outputs counts, or only files surfaced with a send-file action).
- No doc on whether standard Desktop mirrors delivered cloud files into a local folder automatically. Not documented.

## Q3. Reaching a non-connected folder from a cloud session; pre-approval

### Takeaway
Folder access prompts exist for cloud Cowork tasks (documented in the changelog), and a community report shows a session requesting access to a new folder and getting it after the user approved on the computer. Pre-approval is only documented via the admin `isDefaultSelected` field (3P), which "skips the trust prompt". Org settings can also force fresh approval for every permission-gated call. No documented way to pre-approve a specific folder for all future cloud sessions on standard Desktop.

### Cited Findings
- Changelog v1.24012.0 (2026-07-21), Cowork: "Updated folder access prompts for cloud Cowork tasks to note that files Claude uses leave your device and are processed on Anthropic's servers." [DOC] [Changelog](https://claude.com/docs/cowork/changelog)
- Changelog v2.31226.0 (2026-10-08), Cowork: "Fixed Claude asking for access to a folder the session already had, which left scheduled runs waiting on an approval nobody was there to give." [DOC] [Changelog](https://claude.com/docs/cowork/changelog)
- Changelog v1.12603.1 (2026-06-11), Cowork: "Fixed remote sessions re-prompting for access to folders you had already trusted." [DOC] [Changelog](https://claude.com/docs/cowork/changelog)
- Cloud session reaches local files "only while the desktop app is open, only for folders you've connected, and with the permissions you've already set." [DOC] [Web, desktop, and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)
- Org controls for cloud sessions include: "Require fresh approval for every permission-gated tool call by turning off persistent 'always allow,' and control whether members can run sessions without per-call approval prompts." [DOC] [Architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)
- `isDefaultSelected`: "When `true`, the folder appears already selected on the new-task page and skips the trust prompt. Users can remove it." (3P docs) [DOC] [Desktop and filesystem access (3P)](https://claude.com/docs/third-party/claude-desktop/local-access)
- [COMMUNITY] Issue ScottHysom/claude-plugins #297 (opened 2026-09-30): a session started from the mobile app had `"connectedFolders": []`; "After `device_request_folder_access` and approval on the Mac, the same session reached the folder. The grant survived a later context reload." (as summarized from the issue page) [Issue #297](https://github.com/ScottHysom/claude-plugins/issues/297)
- The tool surface in this environment (not public docs) describes `device_request_folder_access` as showing "a permission prompt on whatever client they're using", granting access "for THIS session only", and says "If the user declines or doesn't respond, don't repeat the request". Not a public Anthropic document; treat as observed tool behavior.

### Inferences
- A per-session folder request is possible but needs a human approval each session, which defeats unattended capture, and a Stop hook would need it answered before the session ends.
- The 2026-10-08 fix implies unattended scheduled runs can block on folder approvals; relying on prompts for an automatic file drop is fragile.

### Gaps
- No public doc describes the folder-access request flow for cloud sessions in detail (who sees the prompt, whether it can be persisted as "always allow" for a folder).
- No documented per-folder persistent pre-approval for standard Desktop.

## Q4. Sessions started on web or mobile reaching the computer later

### Takeaway
The current support article says a cloud session can read and write connected folders only while Desktop is open "and the session was started on desktop or is a scheduled task", so web- and mobile-started sessions are documented as unable to reach local folders. A community report contradicts this (a phone-started session reached a folder after a folder access request was approved). There is no documented mechanism for a web/mobile session to reach the computer later when Desktop opens.

### Cited Findings
- "*Local file access, local connectors, browser use, and computer use from web and mobile work through the Claude Desktop app. A cloud session can read and write files in folders you've connected on your computer only while the desktop app is open on that computer and the session was started on desktop or is a scheduled task. If the app is closed, the session keeps running but can't reach your local files." [DOC] [Web, desktop, and mobile, updated this week](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)
- Same article, browser: "When the desktop app is online, the built-in browser is also available in Cowork on web or mobile. A session started on desktop can be steered from web or mobile while the desktop app stays open." [DOC] [Web, desktop, and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile)
- "On web and mobile, your tasks run in the cloud and work with the files and connectors saved to your Claude account, not the files on your computer." [DOC] [Use Claude Cowork safely](https://support.claude.com/en/articles/13364135-use-claude-cowork-safely)
- Architecture FAQ sets no start-surface condition: "A session in the cloud reaches a member's local files or browser only through the Claude Desktop app on that device, only for folders the member has connected, and only while the app is online." [DOC] [Architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview)
- "Scheduled tasks created in the cloud can't use local folders or local connectors." [DOC] [Cowork in the cloud](https://support.claude.com/en/articles/15811196-what-to-expect-with-claude-cowork-in-the-cloud); contradicted in part by the newer surfaces article, which lets a scheduled task reach connected folders ("or is a scheduled task") [DOC] [Web, desktop, and mobile](https://support.claude.com/en/articles/15520349-use-claude-cowork-on-web-desktop-and-mobile), and by the scheduled-tasks article: "Note: If a scheduled task requires local files or apps, it will only run locally." [DOC] [Schedule recurring tasks](https://support.claude.com/en/articles/13854387-schedule-recurring-tasks-in-claude-cowork)
- Dispatch (phone to desktop) is different: "Dispatch works with the local files and apps on your desktop computer, so your computer needs to be awake and the Claude Desktop app open while Claude works. If you want Claude to keep working while your computer is off, start a cloud session instead." [DOC] [Assign tasks from anywhere](https://support.claude.com/en/articles/13947068-assign-tasks-from-anywhere-in-claude-cowork)
- [COMMUNITY] Phone-started session reached the Mac folder after `device_request_folder_access` was approved; reporter says the "started on desktop" line "may be out of date". [Issue #297](https://github.com/ScottHysom/claude-plugins/issues/297)
- [COMMUNITY] tiavelum/claude-mechanics issue #33 (opened 2026-10-05) lists the same conflict between the surfaces, safety and architecture articles and proposes a test; no answer recorded on the page. [Issue #33](https://github.com/tiavelum/claude-mechanics/issues/33)

### Inferences
- For BurnMon, web- and mobile-started sessions cannot be counted on to write to the laptop under the documented rules; any capture for them would have to come from account-side data (delivered files, Compliance API or OTel for admins) rather than a device write.
- Admin-side telemetry is documented: "If you're a Team or Enterprise plan admin, you can use OpenTelemetry (OTel) to monitor Claude Cowork activity across your organization." [DOC] [Architecture overview](https://support.claude.com/en/articles/14479288-claude-cowork-architecture-overview). This is a possible documented alternative channel for cloud usage data, outside this question's scope.

### Gaps
- No documented "deferred delivery" (queue a device write until Desktop comes online).
- The docs conflict on start-surface conditions; only a live test settles current behavior on the user's Team account.
